Our approach

Security at every stage, from the first commit to production

DevelopSecrets and code checks run on the developer machine before each push.
Pull requestSecrets, code, libraries, Dockerfiles, Kubernetes and Terraform files, pipeline files and AI agent checks. A gate decides.
BuildThe image is scanned and gated before it is pushed. A bill of materials (SBOM) is produced.
Deploy to QARunning-app tests: dynamic scanning, API fuzzing, exposure checks, AI red-team probes.
ProductionRuntime controls for agents, detection rules, and the SBOM watched for new vulnerabilities.
Principle. Tools find known patterns; people find design flaws and decide what is acceptable. We will automate the first, and give the second owners, deadlines and a process.

Integrations · for developers

GitHub and SonarQube: what a developer will see and do

What a developer will see

  • A summary on each pipeline run
  • Markers on the risky lines in the pull request
  • One comment on the pull request, updated on every push
  • In SonarQube: code smells, hot-spots and the quality gate for the project

What a developer will do

  • Run one command to add scanning to a repository
  • Put the SonarQube address in one settings file (not secret)
  • Make sure the CI secret exists; one organisation-level secret covers every repository
  • Run a scan on the main branch and check the last lines of the log
Note. SonarQube Community has no branch or pull-request analysis; it reports the main branch. Those features need a paid edition.
Integrations · for the security team

DefectDojo and Dependency-Track: two views no single scan can give

DefectDojo: one register

  • Every scan on the main branch will be sent as an update, not a new import: new findings open, fixed ones close, no duplicates
  • Findings approved as exceptions will appear as accepted risk
  • Owners, fix deadlines, tickets and management reports across all repositories
  • Deliberate: one token with wide rights, kept in a restricted secret and rotated

Dependency-Track: watch after release

  • The SBOM of every main-branch scan will be uploaded
  • It keeps re-checking it against OSV, GitHub advisories and NVD, even when nobody scans that week
  • Alerts when a new vulnerability affects an application already released
  • Answers 'which of our applications use this library?' in seconds
  • The upload key can do nothing except upload SBOMs and read results
Integrations · Wiz and the Azure cloud

Two jobs, two places: scan what is built, scan what is running

In the pipelines (GitHub Actions, Azure DevOps)

  • The Wiz command-line scanner will check code and libraries, Terraform, Kubernetes and ARM files, and built images
  • Without a licence the step is skipped and passes
  • Report-only first; blocking builds on a failed Wiz policy is switched on later
  • Results in the Wiz portal, and in DefectDojo next to the other findings

In the Azure cloud (set up once, in the Wiz portal)

  • Choose the scope: a management group covers every subscription, now and later
  • Create a read-only app registration with the roles Wiz lists; admin consent in Microsoft Entra
  • Wiz then scans VMs, AKS, registries, storage and identities without agents, and shows attack paths
  • Container registries and clusters are connected separately when image and cluster coverage is wanted
Needed from the client. A Wiz licence and a service account for the command-line scanner; rights to grant read-only roles at the chosen Azure scope; outbound access from the CI runners to Wiz. The exact roles and flags will be confirmed against the client's tenant in the pilot.
Key pillars · defensive architecture

Eight strategies we will apply to agentic security

1. Agents as first-class identities

A dedicated non-human identity, scoped credentials and short-lived tokens for every agent.

2. Tool isolation and sandboxing

Anything an agent generates or runs is contained: no host, network or database access.

3. Least privilege and scoped permissions

Default-deny authorisation on every tool call, with argument and ownership rules.

4. Continuous agent red teaming

Attack the running agent in QA with repeatable probes and framework-based testing.

5. Robust guardrails

Checks decided by code that fail closed, never by the model.

6. Human-in-the-loop oversight

No irreversible action runs without a person approving it.

7. Runtime observability and auditing

Tamper-evident records of what the agent did, and detection rules for misuse.

8. Data protection, governance and cryptography

Classify, minimise and mask data; manage keys; map controls to standards.

Code-level and dependency risks

What the scans will find, and the fix that comes with each finding

Secrets in code

Issue. Keys, tokens and passwords committed to files or history are copied into clones, forks and logs.

We will check. Files, optionally git history, and Docker image layers.

Fix. Rotate first, then move to a secret manager. Test credentials never go in git.

Injection and unsafe patterns

Issue. SQL built from strings, shell commands, unsafe deserialisation, path traversal, XSS, weak crypto.

We will check. Several analysers: OWASP Top 10 rules, Python and JavaScript specialists, SonarQube.

Fix. Parameterised queries, input normalisation, fail-closed guardrails; before and after examples are in the cookbook.

Vulnerable packages

Issue. Known CVEs in direct and indirect libraries, and licences that cannot be used.

We will check. Python, Node and Java dependencies, de-duplicated across tools; licence rules; the SBOM.

Fix. Upgrade the parent package; automatic update pull requests.

Infrastructure and running systems

Check settings while they are still files, and test what is running in QA

Infrastructure as code

Dockerfiles, Kubernetes and Helm, Terraform and CloudFormation: root containers, privileged pods, public buckets, open ports, unencrypted databases. Images will be scanned before the push.

Dynamic testing

OWASP ZAP, API fuzzing from the OpenAPI spec, and logged-in scans (basic, cookie, JSON, form, OAuth2 and SSO token flows). If a login fails the scan stops rather than report an anonymous scan as clean.

Exposure checks

From outside: TLS, security headers, CORS, sensitive paths such as /.git, /.env, actuator and telemetry endpoints, and risky open ports.

Boundary. Dynamic testing is not a penetration test. It finds known patterns; business-logic flaws and interactive SSO with MFA need a human test.
Supply chain and CI/CD

Protect the pipeline and the repository, not only the code

Pipeline files

Unpinned actions, script injection, dangerous triggers and excess token permissions in the workflows.

Repository settings

Branch protection, required checks, force-push, secret scanning, CODEOWNERS, so a failing scan can actually block a merge.

What ships

An SBOM, licence rules, automatic dependency-update pull requests, and image signing with build provenance.

Auto-update trade-off. Repositories will follow a moving version tag, so a new check reaches every repository on its next run. Whoever can move that tag can run code in every repository, so the tags are protected and a repository can pin a version.
AI agents

Three parts: find unsafe wiring, attack a running agent, and give the code safe controls

Static checks (pull request)

Agent-specific code rules, an inventory of models, endpoints, tools and MCP servers checked against an approved registry, and a scan of model files.

Red teaming (QA)

19 repeatable probes against a running agent: authentication, injection, tool abuse, excessive agency, leaks. Framework-based testing (OWASP Agents and LLM, NIST AI RMF, MITRE ATLAS, EU AI Act) with an approved model.

Runtime controls (library)

16 reusable controls for agent code: policy engine, fail-closed guardrails, sandbox, egress control, masking, audit log, secrets handling.

Boundary. No red-team approach proves an agent is safe. Paraphrased prompt injection can still beat heuristic checks, so least privilege and human approval carry the weight.

Developer experience

A developer will onboard a repository without help from DevOps

pip install warden          # once, in a virtual environment
warden init                 # adds scanning and the GitHub workflow
warden scan                 # first scan; never breaks the build
warden config show          # what runs and why
warden hook install         # checks before every push

Designed for adoption

  • A small launcher in the repository; no engine to maintain
  • New checks arrive automatically, or a repository pins a version
  • One settings file, read as data and never executed
  • Test credentials from CI secrets, a local store or a prompt; never in git
During runtime · auth engine

Policy decisions made by code that the model cannot talk its way past

PDP: decision point

Default-deny. Roles, scopes, argument rules, ownership and cross-tenant checks. Unknown means deny.

PEP: enforcement point

Intercepts each tool call, asks the PDP, asks a person when policy says so, writes the audit log.

PIP: information point

Context such as risk score, device and hours. A provider that fails means deny.

PAP: administration point

Validate, version and disable policies with an audit trail; a kill switch per tool or agent.

The model may propose an action. Authorisation, limits, approval and output checks are decided by ordinary code. Token exchange, so that tools never see the user token, needs the platform identity provider and vault.

Detection, response and process

What tools cannot provide: noticing an attack, and people who know what to do

Detection

Detection rules for agent workloads, a recipe for sending alerts and audit logs to the SIEM (Sentinel, Datadog), and notifications when a gate fails, a new Critical appears or a deadline is missed.

Process kit

Nine short documents: threat model, code-review checklist, vulnerability policy, incident runbook, access review, training plan, penetration-test scope, security champions.

Boundaries and next additions

What automated scanning does not replace, and what comes next

Still needs people

  • A manual penetration test, before major releases
  • Threat modelling and design review
  • Network, endpoint and cloud operations security
  • Incident response, rehearsed
  • Privacy and data-governance decisions

Next additions to the scanners

Port and service discovery; Known-CVE and misconfiguration templates; Authorisation test pack; Deep TLS testing; Session and token testing; Subdomain / asset discovery and DNS-email checks; Mobile application testing.

These extend the automated part of a penetration test; the manual test itself stays a human activity.
