Point of view

Finding the weakness before an attacker does

How we scan, test and attack our own applications and AI agents: automated scanning on every change, penetration testing on every release, and a clear, honest picture of what is and is not covered.

Cyber security

Keeping systems and data confidential, correct and available, in people, process and technology.

VAPT

Vulnerability Assessment (find the weaknesses) plus Penetration Testing (prove which ones an attacker can really use).

Our approach

One plug-and-play framework for developers, backed by scheduled manual penetration tests for the things tools cannot judge.

Foundations

What cyber security means, and where VAPT fits

Security is the discipline of keeping the CIA triad true against a thinking adversary. VAPT is how we measure whether it is true today.

Confidentiality

Only the right people and systems see the data. Threats: leaked secrets, broken access control, exposed databases.

Integrity

Data and code are not altered without authority. Threats: injection, tampered dependencies, poisoned models, unsigned builds.

Availability

Services work when needed. Threats: denial of service, ransomware, resource exhaustion, runaway agents.

Our point of view

Three layers, each answering a different question

No single tool or test is enough. Automation gives breadth and speed; humans give depth and judgement; detection covers what slips through.

1. Prevent: automate in the pipeline

Secrets, code, dependencies, containers, infrastructure code, workflow files and AI-agent checks run on every pull request. Findings gate the merge by policy.

2. Prove: test the running system

Dynamic scanning, authenticated API fuzzing and external exposure checks against QA. Manual penetration tests for logic, authorisation and chained attacks.

3. Detect and respond

Runtime rules, audit trails, alerts and tickets with remediation deadlines, so problems that escape are seen and closed.

Scan every change. Attack every release. Assume something gets through, and be ready to see it.

The solution

One command for developers, one policy for the organisation

A developer runs three commands and gets a security report on every pull request. Security owns the rules centrally. Nobody needs to learn ten tools.

1 Installsecscan init detects the stack, adds config and the CI file
2 ScanRight tools picked automatically, pinned scanner images, offline-capable
3 GateNormalise, de-duplicate, apply baseline and waivers, fail closed
4 ReportHTML report, pipeline summary, SBOM, control mapping
5 TrackCentral dashboard, SLA clocks, alerts, tickets

Starts report-only

Nothing breaks a build until the team opts in. Presets: starter, standard, strict.

Works on any CI

GitHub Actions verified end to end. Jenkins and Azure DevOps templates provided, not yet run on a live server.

Honest by design

A tool that cannot run is reported as "not run", never as "clean". Required tools cannot be switched off without a dated waiver.

Penetration testing, automated part

Testing the running system, not just the source

Dynamic scan (DAST) Verified

OWASP ZAP baseline against a running QA app; authenticated mode with a bearer token that is never written to logs. Verified on a real FastAPI application.

API fuzzing Verified

Schemathesis generates hostile requests from the OpenAPI spec (bad types, boundaries, auth headers) and reports crashes and contract violations.

External exposure Verified

TLS configuration, security headers, CORS, sensitive paths, risky open ports. On a real host it found Redis and PostgreSQL reachable from the network.

AI agent red teaming Partly verified

21 attack probes (prompt injection, tool abuse, data leakage) against a running agent. Verified against a sample agent; a real-LLM run needs an approved model.

Authorisation first. Active testing is run only against systems we own, in QA, with written scope. Production attack testing is never automatic.

The human part

Manual penetration testing programme

Tools find known patterns. A person finds the flaw in how your application is designed. We run both, on a schedule.

When

  • Before each major release
  • After large architecture changes
  • At least once a year for every internet-facing system
  • After a serious incident

What testers do

  • Business-logic abuse (skip a payment step, replay a request)
  • Authorisation: horizontal and vertical privilege escalation
  • Chaining low findings into one serious path
  • Threat-model-driven abuse cases

Ground rules

  • Written authorisation and scope
  • QA or staging first; production only by agreement
  • Named contacts and a stop condition
  • Data handling and evidence retention rules

Severity

CVSS plus business impact. Critical and High have fixed fix-by dates, tracked on the dashboard.

Retest

Every fixed finding is re-tested and closed with evidence, not trust.

Output

Executive summary, technical detail with reproduction steps, fix guidance, mapping to controls.

AI agent security

Pen-testing agents is different

An agent can read data, call tools and act. The attack is often a sentence, not an exploit.

  • Fail-open guardrails
  • Unregistered models, risky MCP servers
  • Secrets inside prompts
  • Malicious model files

Test while running 21 probes

  • Direct and indirect prompt injection
  • Tool abuse and privilege escalation
  • Data and system-prompt leakage
  • Jailbreaks and unsafe output
  • Run via secscan redteam in QA

Contain at runtime 16 controls

  • Identity and scoped permissions
  • Docker sandbox for code execution
  • Human approval for risky actions
  • Tamper-evident audit log
  • Output lineage, classification, retention
