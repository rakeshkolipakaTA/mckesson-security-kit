Point of view

Securing applications and AI agents: finding weaknesses before attackers do

Our view: every application and AI agent should be scanned on every change, tested while running, and penetration-tested on a schedule. This deck sets out the security problems, the solution we use, what is already proven, and what is still to come.

The problem

More code, more third-party libraries and now autonomous AI agents widen the attack surface faster than manual review can follow.

The approach

Automated checks in the delivery pipeline from day one, a staged move to blocking builds, and scheduled penetration tests for what tools cannot judge.

The outcome

A report per change, a portfolio dashboard, an inventory of software components, deadlines for fixes, and mapping to recognised frameworks.

Summary

The short answer

Security is built into delivery, not added at the end. Automation gives speed and breadth; people give depth and judgement.

What is in place today Ready

  • One-command onboarding of a project, about 10 minutes
  • Secret, code, dependency, container, infrastructure and pipeline scanning
  • Dynamic and API testing of running applications in QA
  • AI-agent checks: 29 static, 21 attack probes, 16 runtime controls
  • Central policy, dashboard, fix-by deadlines, ticket and alert hooks

Where the approach extends next Planned

  • Roll out per project in report-only mode, then enforce
  • Add network, known-vulnerability and access-control testing
  • Schedule manual penetration tests before major releases
  • Connect to ticket, chat and monitoring tools
  • Run AI red-team campaigns against approved models
Our approach

Three layers, each answering a different question

1. Prevent

Checks run on every pull request. Findings are ranked and, by policy, can stop a merge. Problems are fixed when they are cheapest to fix.

2. Prove

The running application is attacked in QA: dynamic scanning, API fuzzing, external exposure checks, and manual penetration tests for what tools cannot judge.

3. Detect and respond

Audit trails, runtime rules, alerts and tickets with deadlines, so anything that slips through is seen and closed.

Scan every change. Attack every release. Assume something gets through, and be ready to see it.

How it runs

From first command to enforced gate

Developers do not need to learn the individual security tools or write pipeline code.

1 OnboardOne command detects the stack and adds config and the pipeline file
2 ObserveReport-only: findings are shown, nothing is blocked
3 BaselineExisting issues recorded; only new ones count
4 EnforceNew Critical and High findings block the merge
5 Release gateStricter checks and image scan before deployment

No disruption

Projects start report-only. Nothing breaks a build until the team decides to turn enforcement on.

Works with common pipelines

GitHub Actions is proven end to end. Jenkins and Azure DevOps templates are provided and still to be validated on live servers.

Policy stays central

Security owns the rules. Projects can add exclusions or time-boxed waivers with an owner and expiry, but cannot silently weaken the policy.

VAPT programme

Manual penetration testing: when and how

Tools find known patterns. A person finds the flaw in how an application is designed. We use both.

When

  • Before each major release
  • After large architecture changes
  • At least yearly for each internet-facing system
  • After a serious incident

What testers do

  • Abuse business logic (skip a step, replay a request)
  • Test horizontal and vertical privilege escalation
  • Chain small findings into one serious path
  • Run abuse cases from the threat model

Ground rules

  • Written authorisation and scope
  • QA or staging first; production only by agreement
  • Named contacts and a stop condition
  • Rules for data handling and evidence retention

Severity

CVSS plus business impact. Critical and High have fixed fix-by dates.

Retest

Every fix is retested and closed with evidence.

Output

Executive summary, technical detail with reproduction steps, fix guidance, control mapping.

AI agent security

Securing agents is different

An agent can read data, call tools and act. The attack is often a sentence, not an exploit.

Prevent in code 29 checks

  • Unsafe tools (shell, eval, open HTTP)
  • Guardrails that fail open
  • Unregistered models and risky MCP servers
  • Secrets inside prompts
  • Malicious model files

Test while running 21 probes

  • Direct and indirect prompt injection
  • Tool abuse and privilege escalation
  • Data and system-prompt leakage
  • Jailbreaks and unsafe output

Contain at runtime 16 controls

  • Identity and scoped permissions
  • Docker sandbox for code execution
  • Human approval for risky actions
  • Tamper-evident audit log
  • Output lineage, classification, retention

Mapped to the OWASP LLM Top 10, NIST AI RMF, ISO 42001 and the EU AI Act through one control crosswalk.

  • Close the easy wins: secrets, library upgrades
  • Connect dashboard and tickets
  • Agree penetration-test scope and rules

60 days: enforce and extend

  • Turn on the blocking gate for pilot projects
  • Add network, known-vulnerability and TLS testing to QA scans
  • Role-based access-control test pack
  • First scheduled manual penetration test
  • Cluster and cloud posture runs

90 days: mature

  • Strict release gate with signed images
  • Real-model AI red-team campaign
  • Runtime detection connected to monitoring
  • Joint red and blue team detection exercise
  • Quarterly review of waivers and deadlines
Prerequisites

What an organisation needs in place to adopt this

Scope and authority

  • Which systems are in scope for active testing, and who signs the authorisation
  • Approval to scan company-owned network ranges
  • An approved model endpoint for AI red teaming

Access and environment

  • A pipeline runner that can reach the dashboard
  • A QA environment for dynamic testing
  • A Kubernetes cluster and cloud account for posture checks
  • An internal package index for the installer

People

  • A security contact to receive alerts and triage overdue findings
  • Owners for each project to act on findings
  • Compliance contact to map sector-specific requirements

Decisions

  • Which projects pilot first, and the enforcement date for each
  • Budget and vendor for external penetration testing
